`bejamas/ui` follows shadcn/ui closely: the same component names, the same anatomy, the same `data-slot` attributes, and the same shared styles (Vega, Nova, Lyra, Maia, Mira, Luma). If you know shadcn/ui, most of `bejamas/ui` will feel familiar.

But it is **not a line-by-line port**. Components are Astro files rendered on the server, interactivity comes from [`@data-slot`](https://data-slot.com) vanilla controllers instead of React, and a handful of shadcn/ui components are not available yet.

:::note
`bejamas/ui` aligns with shadcn's **Base UI** flavour. Radix-flavour differences are called out where relevant.
:::

## At a glance

| | Count |
| --- | --- |
| Components shadcn/ui and bejamas/ui both ship | **39** |
| ↳ Drop-in (same parts, same props) | 12 |
| ↳ Close (same anatomy, some props or parts differ) | 25 |
| ↳ Different API (materially different anatomy) | 2 |
| shadcn/ui components bejamas/ui does not ship | **20** (+ `form` and 3 docs-only recipes) |
| bejamas/ui-only components | **6** |

**What the verdicts mean:**

- **Drop-in** — Same sub-components and same props. Porting shadcn/ui markup only needs the general React → Astro translation described in [Astro props vs React props](#astro-props-vs-react-props) (`className` → `class`, event handlers → events, and so on).
- **Close** — Same anatomy, but some props, variants or sub-components are missing, renamed or behave differently. Each one has porting notes below.
- **Different API** — The anatomy or API differs enough that you should read the porting notes before copying code.

## Astro props vs React props

This is the single biggest difference between the two libraries, and it applies to **every** component — including the ones marked drop-in. shadcn/ui components are React client components; `bejamas/ui` components are `.astro` files that render HTML on the server. That changes what a "prop" can be.

### Quick translation table

| shadcn/ui (React) | bejamas/ui (Astro) |
| --- | --- |
| `className="…"` | `class="…"` |
| `htmlFor="email"` | `for="email"` |
| `colSpan={2}`, `tabIndex={0}` | `colspan={2}`, `tabindex={0}` (HTML attribute names) |
| `style={{ width: 200 }}` | `style="width: 200px"` (prefer a string) |
| `children` | default `<slot />` |
| `render={<a href="/" />}` (Base UI) / `asChild` (Radix) | `as="a"` on components that support it, `asChild` on triggers, or `data-slot` on your own element — see [Composition](#composition-render-aschild-and-as) |
| `value` + `onValueChange` (controlled) | `defaultValue` + listen for `<component>:change` |
| `open` + `onOpenChange` | `defaultOpen` + listen for `<component>:change` |
| `onClick`, `onSelect`, `onCheckedChange` … | native DOM events or `<component>:*` CustomEvents in a `<script>` |
| imperative `ref` / `setApi` | `id` + `document.getElementById()` + `<component>:set` events |
| `"use client"`, `client:load` | not needed — behaviour is attached by the component's own `<script>` |
| `React.ComponentProps<"div">` | `HTMLAttributes<"div">` from `astro/types` |

### Props must serialize to HTML

An Astro component renders once, on the server (or at build time). Its props end up as HTML attributes, so they have to be serializable:

- **No function props.** There is no `onValueChange`, `onOpenChange`, `onClick`, `filter`, `itemToStringLabel` or render-function children. Behaviour is wired up in a `<script>` instead.
- **No React context.** Sub-components don't talk to each other through context. They find each other through the DOM (`data-slot` attributes) once the page loads.
- **No `ref`.** Give the element an `id` and query it.
- **Strings and numbers, mostly.** `Select`, `Combobox` and `ToggleGroup` values are always strings. Arrays are accepted where documented (for example `Accordion defaultValue={["a", "b"]}`).

### State is uncontrolled: initial props + events

shadcn/ui lets you control state with React (`value` + `onValueChange`). In `bejamas/ui` every interactive component is **uncontrolled**: props only set the **initial** state, and the `@data-slot` controller owns the state after that.

- **Initial state props** — `defaultValue` (Tabs, Accordion, ToggleGroup, Select, Combobox, RadioGroup, Command, DropdownMenu, Slider), `defaultOpen` (Dialog, Drawer, HoverCard, DropdownMenu, CommandDialog, HamburgerMenu), `defaultChecked` (Switch, DropdownMenu items). A few components use a different name for the same idea: `Collapsible` takes `open`, and `Switch` (`checked`) and `Slider` (`value`) also accept the shadcn-style name, but it still only sets the initial state.
- **Change events** — every interactive component dispatches a `<component>:change` CustomEvent on its root (for example `tabs:change` with `{ value }`, `dialog:change` with `{ open }`). Some also dispatch more specific events such as `command:select`, `select:open-change` or `slider:commit`.
- **Programmatic control** — dispatch `<component>:set` on the root (for example `tabs:set` with `{ value: "account" }`, `dialog:set` with `{ open: true }`).
- **Styling state** — components expose `data-state`, `data-open` / `data-closed`, `data-checked`, `data-disabled` and similar attributes. `bejamas/tailwind.css` registers the same custom variants as shadcn's `tailwind.css` (`data-open:`, `data-closed:`, `data-checked:`, `data-unchecked:`, `data-selected:`, `data-disabled:`, `data-active:`, `data-horizontal:`, `data-vertical:`).

Here is a controlled dialog in shadcn/ui:

```tsx title="shadcn/ui (React)"
const [open, setOpen] = useState(false);

<Dialog open={open} onOpenChange={setOpen}>
  <DialogTrigger render={<Button variant="outline" />}>Open</DialogTrigger>
  <DialogContent>…</DialogContent>
</Dialog>;
```

And the same thing in `bejamas/ui`:

```astro title="bejamas/ui (Astro)"
<Dialog id="settings-dialog">
  <Button variant="outline" data-slot="dialog-trigger">Open</Button>
  <DialogContent>…</DialogContent>
</Dialog>

<Button id="open-settings">Open from elsewhere</Button>

<script>
  const dialog = document.getElementById("settings-dialog")!;

  // React to changes (replaces onOpenChange)
  dialog.addEventListener("dialog:change", (event) => {
    console.log("open:", (event as CustomEvent).detail.open);
  });

  // Change state from code (replaces setOpen(true))
  document.getElementById("open-settings")!.addEventListener("click", () => {
    dialog.dispatchEvent(new CustomEvent("dialog:set", { detail: { open: true } }));
  });
</script>
```

### Composition: `render`, `asChild` and `as`

shadcn/ui composes with `render={<Button />}` (Base UI) or `asChild` (Radix), which merges the component's behaviour into your element. Astro can't clone and merge props into a child element, so `bejamas/ui` offers three alternatives:

1. **`as` prop** — on `Button`, `Badge`, `AvatarGroup`, `AvatarGroupCount`, `ItemGroup`, `CarouselPrevious`, `CarouselNext` and `StickySurface`. The most common case is a link that looks like a button:

   ```tsx title="shadcn/ui"
   <Button render={<a href="/login" />} nativeButton={false}>Login</Button>
   // or, as the shadcn docs recommend
   <a className={buttonVariants()} href="/login">Login</a>
   ```

   ```astro title="bejamas/ui"
   <Button as="a" href="/login">Login</Button>
   ```

2. **`asChild` on triggers** — `DialogTrigger`, `PopoverTrigger`, `TooltipTrigger`, `HoverCardTrigger`, `DropdownMenuTrigger`, `CollapsibleTrigger` and `AccordionTrigger` accept `asChild`. Unlike Radix, this renders a **wrapper** `<div data-slot="…-trigger" data-as-child>` around your element instead of merging into it. ARIA attributes land on the wrapper, and other props passed to the trigger are not forwarded — put them on the child.

3. **`data-slot` on your own element** — because the controllers find parts by `data-slot`, you can turn any element into a part. This is the closest equivalent to `render`:

   ```astro
   <Button variant="outline" data-slot="dialog-trigger">Open</Button>
   <Button variant="ghost" data-slot="dialog-close">Cancel</Button>
   ```

Some triggers are already styled buttons. `PopoverTrigger` and `DropdownMenuTrigger` render a `bejamas/ui` `Button` and accept its `variant` and `size` props directly — write `<PopoverTrigger variant="outline">` instead of `<PopoverTrigger render={<Button variant="outline" />}>`. Note that their default variant is `default` (a filled primary button), not an unstyled trigger.

### Slots instead of children

`children` becomes Astro's default `<slot />`. A few components also accept **named slots** for parts you would otherwise replace by editing the component:

| Component | Named slots |
| --- | --- |
| `AccordionTrigger` | `icon` — replaces the chevron |
| `SelectContent` | `scroll-up`, `scroll-down` — replaces the scroll button contents |
| `HamburgerMenu` | `brand`, `actions`, `footer` |

```astro
---
import { PlusIcon } from "@lucide/astro";
---

<AccordionTrigger>
  Is it accessible?
  <PlusIcon slot="icon" />
</AccordionTrigger>
```

### JavaScript, hydration and View Transitions

- **Zero JS by default.** 23 of the 45 component families ship no client JavaScript at all (Button, Card, Badge, Field, Input, Table, …). The rest attach a small bundled `<script>`, usually a `@data-slot` controller — you never add a `client:*` directive. See [Design Principles](/docs/design-principles) and [How bejamas/ui ships less JavaScript than shadcn/ui](/blog/how-bejamas-ui-ships-5x-less-javascript-than-shadcn-ui).
- **Initialization runs on page load.** Each component script binds the elements present when the page loads. If you inject markup later, or use Astro's `<ClientRouter />`, call the controller yourself (for example `createDialog(el)` from `@data-slot/dialog`) for the new elements.
- **Native forms.** `Select`, `Combobox`, `RadioGroup` and `Switch` take `name` (and `required` where relevant) and generate hidden native inputs, so they submit with a plain `<form>` — no form library required. `Slider` does not generate an input yet; mirror its value from `slider:change` into a hidden input if you need to submit it.

## Porting notes

Each note lists only what changes beyond the general translation in [Astro props vs React props](#astro-props-vs-react-props). Each note links to the component's docs page.

### Drop-in components

These need only the general React → Astro translation. Good to know:

- **Textarea** — pass initial text as children, or with `value` / `defaultValue`.
- **Field** — set `data-invalid` on `Field` and `aria-invalid` on the control yourself, as in shadcn/ui. `FieldError` also takes `forceMount` for client-side validation.
- **Input Group** — the group gets `data-disabled` automatically from the control's `disabled` attribute.
- **Radio Group, Switch** — submit natively with `name`. Listen for `radio-group:change` or `switch:change`.
- **Kbd** — `KbdGroup` renders a `<div>`, so don't nest it inside a `<p>`.
- **Table** — there's no equivalent of shadcn's [Data Table](https://ui.shadcn.com/docs/components/base/data-table) guide. Use the static `Table` with server-side sorting and pagination, or your own script.

| `<Toggle pressed={…} onPressedChange={…}>` | `<Toggle defaultPressed>` + `toggle:change` |
| `data-pressed:` classes | `aria-pressed:` or `data-[state=on]:` classes |
| `toggleVariants` from the toggle component | `toggleVariants` from `lib/toggle-shared` |

#### Toggle Group

<small>[Docs →](/components/toggle-group)</small>

| shadcn/ui | bejamas/ui |
| --- | --- |
| `<ToggleGroup type="multiple">` (Radix) | `<ToggleGroup multiple>` |
| `<ToggleGroup>` | `<ToggleGroup spacing={2}>` to match shadcn's default spacing |

**Watch out:** when both the group and an item set `variant` or `size`, the item wins. In shadcn, the group wins.

#### Tooltip

<small>[Docs →](/components/tooltip)</small>

| shadcn/ui | bejamas/ui |
| --- | --- |
| `<TooltipProvider delay={0}>` | remove it and set `delay={0}` on each `Tooltip` |
| `delayDuration={…}` (Radix) | `<Tooltip delay={…}>` |
| `<TooltipTrigger render={<Button />}>` | `<TooltipTrigger asChild><Button>…</Button></TooltipTrigger>` |

**Watch out:** the default delay is 300 ms, and the `Tooltip` root renders an `inline-block` wrapper element.

### Different API components

#### Carousel

<small>[Docs →](/components/carousel)</small>

`bejamas/ui` uses native CSS scroll snapping with a `@data-slot/carousel` controller instead of Embla.

| shadcn/ui | bejamas/ui |
| --- | --- |
| `<Carousel>` | `<CarouselRoot>` (the `bejamas/ui` `Carousel` is an all-in-one widget with built-in controls) |
| `<CarouselItem>` | `<CarouselSlide>` |
| `-ml-4` on `CarouselContent` and `pl-4` on items | nothing; `CarouselContent` already uses `gap-4` |
| `opts={{ loop: true }}` | `data-loop="true"` |
| `setApi` + `api.on("select")` | `carousel:change` and `data-index` on the root |

**Not available:** `plugins`. For autoplay, dispatch `carousel:set` with `{ action: "next" }` from a timer.

**Watch out:** `CarouselPrevious` and `CarouselNext` sit in normal flow instead of overlaying the slides, so place them yourself.

#### Drawer

<small>[Docs →](/components/drawer)</small>

shadcn ships two drawers: Base UI (`swipeDirection`, snap points) and Radix/vaul (`direction`). The `bejamas/ui` Drawer has its own API, and also covers shadcn's Sheet.

| shadcn/ui | bejamas/ui |
| --- | --- |
| `<Drawer swipeDirection="down">` (Base UI) or `<Drawer direction="bottom">` (Radix) | `<Drawer side="bottom">` |
| `<Sheet>` + `<SheetContent side="right">` | `<Drawer side="right">` + `<DrawerContent>` |
| `<DrawerTrigger render={<Button />}>` | `<Button data-slot="drawer-trigger">` |
| `<div className="p-4">` around the content | `<DrawerBody>` |
| `[data-slot=drawer-overlay]` selectors | `[data-slot=drawer-backdrop]` |

**Not available:** a top drawer, snap points, `showSwipeHandle`, `DrawerPortal` and `DrawerOverlay`.

**Watch out:** the default side is `right` (shadcn: bottom), and there's no built-in close button. Add one with `data-slot="drawer-close"`.

## What bejamas/ui does not offer

These shadcn/ui components don't have a `bejamas/ui` equivalent yet.

| shadcn/ui | What it is | Closest option in bejamas/ui |
| --- | --- | --- |
| Alert Dialog | Blocking confirmation modal | `Dialog` with `closeOnClickOutside={false}` and your own action buttons (`data-slot="dialog-close"`). |
| Aspect Ratio | Fixed-ratio box | Tailwind `aspect-video`, `aspect-square` or `aspect-[4/3]`. |
| Calendar | Date / range grid (`react-day-picker`) | `<Input type="date">`, or a React island. |
| Chart | Recharts wrappers | A React island, a framework-agnostic chart library, or server-rendered SVG. |
| Context Menu | Right-click menu | A React island. `DropdownMenu` only opens from a trigger. |
| Direction | React RTL provider | Not needed: set `dir="rtl"` on `<html>` (`bejamas init --rtl --lang ar`). |
| Empty | Empty-state layout | Compose `Card` or `Item` with `SemanticIcon`. |
| Input OTP | Segmented one-time-code input | `Input` with `autocomplete="one-time-code"`, `inputmode="numeric"` and `maxlength`. |
| Menubar | Desktop-style menu bar | A row of `DropdownMenu`s, or a React island. |
| Pagination | Page links | `Button as="a"` links inside a `<nav>`. |
| Progress | Progress bar | Native `<progress>` or `<meter>`. |
| Scroll Area | Custom scrollbars | `overflow-auto` with the `no-scrollbar` and `scroll-fade-*` utilities from `bejamas/tailwind.css`. |
| Sheet | Side panel | `Drawer` with `side="left"`, `"right"` or `"bottom"`. |
| Sidebar | Application sidebar | `<aside>` with `Collapsible` sections and a `Drawer side="left"` on mobile. |
| Form | `react-hook-form` wrappers (legacy, new-york-v4 only) | `Field` + a native `<form>` + [Astro Actions](/docs/forms-astro-actions). |
| Data Table (recipe) | TanStack Table guide | Static `Table` plus server-side or client-side logic. |
| Date Picker (recipe) | Popover + Calendar | `Popover` with `<Input type="date">`. |
| Typography (recipe) | Prose styles | `@tailwindcss/typography` or your own prose CSS. |

### AI and chat components

shadcn/ui includes components for chat and agent interfaces. `bejamas/ui` doesn't ship these yet:

| shadcn/ui | What it is |
| --- | --- |
| Attachment | File or image chip with upload state |
| Bubble | Chat bubble with variants, groups and reactions |
| Marker | Inline status or system note in a conversation ("Thinking…") |
| Message | A single chat message with avatar, header and footer |
| Message Scroller | Chat transcript scroller that follows streamed output |
| Questionnaire | Multi-step question form for agents asking the user questions |

Attachment, Bubble, Marker and Message are plain markup in shadcn/ui and can be ported to Astro by hand. The `shimmer` utility used for streaming states is already available in `bejamas/tailwind.css`.

### Using shadcn/ui React components alongside bejamas/ui

If you need one of the components above today, you can run a shadcn/ui React component as an [Astro island](https://docs.astro.build/en/concepts/islands/) next to `bejamas/ui`: add the React integration (`npx astro add react`), copy the component's source and its dependencies from [ui.shadcn.com](https://ui.shadcn.com), and render it with a `client:*` directive. Both libraries use the same design tokens and CSS variables, so the island matches your theme. Keep in mind that each island ships React to the browser.

## Beyond components

### CLI and registry

The `bejamas` CLI is a thin, Astro-first wrapper around a pinned version of the shadcn CLI. It uses the same registry item format, so `components.json` and `registries` work the way you expect from shadcn.

| Task | shadcn | bejamas |
| --- | --- | --- |
| Create a project | `shadcn init` | `bejamas init` (Astro app, monorepo, or monorepo + docs) |
| Add components and blocks | `shadcn add` | `bejamas add` (rewrites imports for Astro and installs components into per-component folders) |
| Presets | `shadcn apply`, `shadcn preset` | `bejamas apply`, `bejamas preset` (decode, url, open, resolve) |
| Project info | `shadcn info` | `bejamas info` (proxies shadcn) |
| Generate docs from components | — | `bejamas docs:build`, `bejamas docs:check` |
| Browse, build registries, MCP | `shadcn view`, `search`, `build`, `registry`, `mcp` | Use the shadcn CLI directly |

`bejamas/ui` serves a registry per style (`bejamas-juno`, `bejamas-vega`, `bejamas-nova`, …) instead of shadcn's `base-*` / `radix-*` style names, and its `components.json` has no `rsc` / `tsx` fields but adds an `aliases.docs` entry. See the [CLI docs](/docs/cli).

### Styles, themes and fonts

| | shadcn/ui | bejamas/ui |
| --- | --- | --- |
| Styles | Vega, Nova (default), Maia, Lyra, Mira, Luma, Sera, Rhea | **Juno** (default, Bejamas-authored), Vega, Nova, Lyra, Maia, Mira, Luma |
| Themes | 24 | The same 24, plus 8 Bejamas themes (`bejamas-blue`, `bejamas-neon-yellow`, `bejamas-apple`, `bejamas-orange`, `bejamas-sunflower`, `bejamas-violet`, `bejamas-turquoise`, `bejamas-magenta`) |
| Design tokens | `background`, `primary`, …, `chart-1`–`5`, `sidebar-*`, `radius` | The same token names |
| Fonts | 26 | 24 (no EB Garamond or Instrument Serif yet) |
| Icon libraries | Lucide, Hugeicons, Tabler, Phosphor, Remix Icon — rewritten at **install** time | The same five — resolved at **render** time by `SemanticIcon` |

The Sera and Rhea styles aren't available in `bejamas/ui` yet. Preset codes that only use shared values decode the same way in both CLIs; Bejamas-only values (Juno, the Bejamas themes) only work with the `bejamas` CLI.

Because the token names are identical, a theme generated for shadcn/ui works with `bejamas/ui` and vice versa. See [Theming](/docs/theming).

### Utilities

- **`cn()`** — `bejamas/ui` builds `cn` from `clsx` and `tailwind-merge`. shadcn/ui imports it from the `cn` package; both behave the same.
- **Tailwind utilities** — `bejamas/tailwind.css` provides the same custom variants as shadcn's `tailwind.css`, plus the `shimmer`, `scroll-fade-*` and `no-scrollbar` utilities.
- **Hooks** — shadcn's only hook, `useIsMobile`, exists to support Sidebar. `bejamas/ui` has no hooks; responsive behaviour uses CSS.

### Dark mode, RTL and forms

- **Dark mode** — Both use a `.dark` class on `<html>` set by an inline script. The `bejamas/ui` dark mode guide builds an Astro theme switcher with no hydration instead of a React `ModeToggle` or `next-themes`. See [Dark Mode](/docs/dark-mode).
- **RTL** — shadcn/ui converts physical classes to logical ones when installing (`--rtl`, `shadcn migrate rtl`). `bejamas init --rtl --lang <ar|fa|he>` sets up `dir` and i18n wiring; there is no install-time class transform.
- **Forms** — shadcn/ui documents React Hook Form, TanStack Form, Formisch and Next.js Server Actions. `bejamas/ui` uses native forms with [Astro Actions](/docs/forms-astro-actions) and the same `Field` components.

### Docs and tooling

- `bejamas/ui` generates component docs from JSDoc comments inside each `.astro` file (`bejamas docs:build`, `bejamas docs:check`). See [Auto-generated Docs](/docs/auto-generated-docs).
- A [Starlight](https://starlight.astro.build) theme (`starlight-theme-bejamas`) is available for documentation sites.
- shadcn/ui additionally offers an MCP server and agent skills for its registry.
